# Capture/UVC 相机网页接入

网页后端通过 Python `ctypes` 调用相邻 `capture` 项目的 `capturecore` 1.x 公共 C ABI，与 `capture.exe` 复用同一采集内核。适配代码在 `src/capture_uvc/`，不复制或修改 capture 源码，不启动桌面界面。默认 DLL 位于 `../capture/build/bin/capturecore.dll`，依赖 DLL 需与它放在同一目录，并与 Python 位数一致。启动其他相机来源时不会加载该 DLL。

## 使用步骤

在 Windows PowerShell、项目根目录 `E:\A-codehub\vision_learning` 执行下面命令：启动本地网页服务并自动打开浏览器。无需管理员权限，也不需要下载依赖；相机在点击连接后才会开始采集。

```powershell
python scripts/camera_web.py
```

1. 停止 `capture.exe` 或其他程序对目标设备的采集。同一相机不能同时由桌面程序和网页开流。
2. 浏览器访问 `http://127.0.0.1:8765`，在“相机来源”选择 **Capture/UVC 相机**。
3. 点击“刷新设备”，选择 **USB Camera · USB 0BDA:1376**。列表也可能包含内置相机和虚拟摄像头，应按名称和 USB 标识选择目标设备。
4. 在“采集格式”选择设备实际列出的像素格式、分辨率和标称帧率，或使用自动策略（优先 MJPEG，其次最大分辨率和最高帧率）。更换内核路径后，先保存配置，再刷新设备。
5. 点击“连接相机”。实时画面显示原生采集 FPS、网页预览尺寸和浏览器 FPS；这几项数值含义不同。
6. 使用共用的手动拍照、自动拍照和录像按钮。照片和录像默认写入 `data/camera/photos/` 和 `data/camera/videos/`，可在输出设置中修改。
7. 更换设备、格式或 DLL 前先断开。关闭或刷新网页会请求断开；正常结束服务也会收尾录像、释放会话。断开后可重新连接。

连接信息保存于 `configs/camera/camera.yaml` 的 `capture_uvc` 段：

```yaml
source_type: capture_uvc
capture_uvc:
  library_path: ../capture/build/bin/capturecore.dll
  device_id: <网页枚举出的稳定设备 ID>
  format_index: -1  # 自动；其他值必须来自该设备的格式列表
```

## 输出与性能

- **预览**：只读取最新帧，不让浏览器累积旧画面。MJPEG 原尺寸时直接传输 JPEG 字节；只有缩小预览或使用原始像素格式时才转换编码。页面的最大宽高仅限制网页预览，不改变拍照和录像尺寸。
- **拍照**：调用原生曝光判稳快照。MJPEG 字节直接保存 JPG；YUYV、NV12、RGB24、BGRA 快照按公共接口的原始像素契约读取后编码为真正的 JPG，保留原始尺寸。曝光判稳可能使单次拍照耗时超过设定间隔；自动拍照跳过错过的时点，不突发补拍，停止时会等待正在进行的快照完成。
- **AVI**：MJPEG 原始帧直通封装，不经过 OpenCV 录像器。只有 MJPEG 采集格式可选用此路径，其他格式会明确报错。
- **MP4**：调用内核 H.264 录像，按其 NVENC→QSV→AMF→libx264 顺序尝试。实际编码器和写入帧数在停止录像后显示。内核录像按原有实现执行，编码或磁盘过慢仍可能拖低采集速度；网页预览独立并不保证录像永不受主机负载影响。
- **统计**：不把标称 FPS 当作实际 FPS，不把未知的录像丢帧数显示成 0。“帧龄”从后端观察到新帧时起算，不是相机曝光到屏幕的完整延迟。内核设备时间戳保持原语义，不能直接当作 Unix 时间。

## 成像参数

连接后，“成像参数”面板通过 `cap_prop_list/get/set/set_auto` 读取和设置当前设备的属性，包括驱动实际提供的曝光、增益、白平衡、亮度等。只显示本机返回的属性，使用设备返回的范围、步长、单位和菜单值；UVC 增益不假定为 dB。每项点击“应用”后即时写入，再回读全部参数；驱动可能将请求值换算到其支持的档位，以回读值为准。

自动模式控制、只读或临时禁用的项目不可直接写值。先应用对应的自动开关或曝光模式，再修改解锁的参数。点击“刷新成像参数”可重新读取设备现值和可写状态。参数不保存到网页 YAML，重新连接后以设备实际状态为准。

同一相机跨平台能力可能不同：若 Windows 驱动未暴露曝光，网页会明确提示，无法仅凭该面板恢复 60 FPS。此来源仍不提供处理区域和 MVS 硬件 ROI。

## 本机验证记录（2026-10-17）

使用 `USB Camera（0BDA:1376）`、MJPEG 1280×720 / 标称 60 FPS 验证了网页 API 的手动和自动拍照、AVI 与 MP4 录制、停止收尾、断开和重新连接。照片为 1280×720，两段约两秒的测试录像均可解码，各写入 60 帧；当时采集约 30 FPS。AVI 实际编码器为 `passthrough`，MP4 为 `libx264`。

MP4 测试时 NVENC 报告所需 API 13.0、驱动仅提供 12.2，随后其他硬编尝试未成功，内核回退到 CPU 编码；没有更改驱动或 capture 内核。Chrome 浏览器实测已完成设备与格式选择、拍照、AVI 开始/停止及 640×360 预览缩放；390 像素宽度下无横向溢出，未发现 JavaScript 异常。该记录是功能验收，未做与桌面程序在相同条件下的性能基准对比。

测试照片、录像和结果留在 `data/camera/capture_uvc_acceptance/`，浏览器验收输出在 `data/camera/capture_uvc_browser_check/`，均不纳入 Git。原有相机配置未被验收脚本覆盖。

成像参数追加验收（旧内核记录，曝光不可控结论已由下方验证更正）：当时 Windows 内核返回 11 项属性，未返回曝光模式、曝光时间或增益。通过网页相同 API 验证了亮度修改与回读、关闭自动白平衡后色温解锁与写入，随后恢复原值；未停止用户的采集会话。Chrome 验证了参数面板、自动白平衡锁定、空能力提示和 390 像素宽度布局；曝光模式与曝光时间的联动使用模拟设备验证。追加验收结果位于 `runs/uvc_properties_check/`，不纳入 Git。

## 画质与 ROI 调整验证（2026-10-18）

发现相邻 `capture` 仓库的 Windows 属性映射混用了从 1 编号的 KS 属性与从 0 编号的 IAM 枚举，导致曝光误显示为变焦、部分成像控件名称与实际参数不符。Windows 后端已改为 SDK 命名枚举，并修正 IAM 曝光整数 log2(秒) 到微秒的换算。对应修复位于该仓库本地分支 `fix/windows-imaging-property-mapping`、提交 `c7cf58e`。需要使用包含该修复并重新编译的 `capturecore.dll`；仅更新本网页代码不能修复旧 DLL。替换 DLL 后须重启 Python 服务，重新加载内核。

在本机 USB 0BDA:1376 上，新内核实际返回 14 项属性，已提供曝光模式和曝光时间，仍未提供增益。验证了自动曝光切换为手动后曝光输入解锁、15625 µs 和 7813 µs 的写入与回读，随后恢复原来的自动曝光模式和曝光档位。当前约 30 FPS、1280×720。自动曝光下画面会随环境和设备内部控制变化；短曝光在现场光照下明显偏暗，应配合补光调节，不能直接认定固定短曝光就能改善所有模糊。未取得昨天同场景的参数和画面，未确认跨日画质变化的唯一原因或实际增益值。

右侧检测 ROI 可在停止监测后拖动框内移动，拖动八个边角控制点缩放，也可继续输入原始像素坐标。控制点不能越过画面边界；Esc 或指针取消会恢复本次拖动前的区域；检测期间锁定编辑，下次开始时应用。Chrome 实测覆盖八个方向缩放、移动越界、最小宽度、取消恢复、预览缩放后的坐标换算、重新框选和检测期间锁定。

## 画质复查与并排调参（2026-10-18）

相机设置原先将成像参数放在完整预览下方，调节靠后的参数时画面会离开视野。现改为桌面左右各约半屏：左侧预览，右侧成像参数独立滚动；输出尺寸工具位于预览下方。预览仍可等比缩放，仅改变显示大小。800 像素及以下恢复上下布局，避免窄屏挤压。Chrome 实测覆盖 1440×900、1366×768、1040×720、390×844，以及主页面内嵌相机页；桌面滚至最后一项参数时画面仍完整可见，无横向溢出。MVS、DroidCam、OBS 的控件显示也已检查，未在本轮连接这些来源的硬件。

用户确认本机设备为直接通过 USB 连接的摄像头模组。本轮继续使用原 Capture 内核接口，并用同一设备的 Windows IAM/KS 只读查询核对能力，得到以下结果：

- **增益不可控是驱动能力限制**：IAM 的 `VideoProcAmp_Gain` 查询范围和当前值均返回 `0x80070490`；标准 KS 增益查询同样返回该错误。未取得实际增益值，不能断言增益过高，也未添加无法生效的增益滑块。驱动也未暴露对焦控制。
- **曝光、锐度写入确实影响原始画面**：手动曝光 1953、7813、31250 µs 的平均灰度分别约为 1.9、18.4、80.1；较长的 62500 µs 约为 127.8。锐度 0 与 100 的原始画面细节和噪声表现也不同。现场短曝光明显偏暗，不能把延长曝光作为高速传送带的画质修复。
- **自动曝光的回读值不代表实际曝光**：先设置手动曝光 1953 或 31250 µs，再开启自动曝光，驱动仍分别回读此前的手动值，但画面平均灰度均约为 124。因此页面将“设备当前值”改为“设备回读值”，并提示自动模式可能返回保留的手动值；不能凭该数值判断实际曝光时间或运动拖影。
- **模糊已存在于设备输出**：原生 MJPEG 为 1280×720，当前网页不缩小时直接传输其 JPEG 字节。绕过网页，使用同一内核分别取得 MJPEG、未压缩 NV12 和 YUYV 帧，三者的静止边缘仍发虚。排除了网页布局、预览缩放和 JPEG 压缩作为本次模糊的主要来源。较长手动曝光减轻部分颗粒感后，边缘仍模糊，继续检查镜头对焦。

随后用户确认镜头上有可旋转部件，转动后画面明显变清楚。再次读取实时原帧，与调整前图像对比，扇贝纹理、螺丝和静止金属边缘均明显清晰；曝光模式仍为自动、曝光回读仍为 7813 µs、锐度仍为 85，未通过软件改变这些参数。结合用户的手动调焦操作和图像变化，确认本次主要模糊由镜头失焦、焦点与当前拍摄距离不匹配造成，网页的曝光或锐度无法代替光学对焦。具体为何跨日失焦未能还原，实际增益仍未知；未在本轮验证高速运动下的拖影。前后对比图为 `.pytest_cache/camera-quality/focus-comparison.jpg`。

本轮实测原帧、对比图和临时诊断脚本保存在 `.pytest_cache/camera-quality/`，不纳入 Git。格式比较完成后已恢复自动选择格式、原曝光模式与档位、原锐度，并重连相机；未修改用户的 YAML 配置，未修改或推送相邻 Capture 仓库。
